HKU ECIC 选课参考站

港大 CDS 学院 ECIC 专业的选课参考站——收录 26 门课的真实学长姐评价，支持按标签筛选 + 个人打分排序，已上线、有真实用户。

React 19 + TypeScript Vite Tailwind CSS v4 真实用户产品 隐私优先设计
🌐 访问线上版本 ⌨️ 查看源码
1

项目背景

港大 CDS 学院的 ECIC（Electronic Commerce and Internet Computing） 是一个交叉学科专业，课程横跨 ICOM / ECOM / FITE / COMP 四大类。 每届新生选课前最大的问题是："这门课到底水不水？老师给分狠不狠？workload 真的大吗？"

这些信息官方 syllabus 不会写、教授不会说、教务不会整理，只能靠往届学长姐在小红书、微信群口口相传。 我观察到三个具体问题：

  • 信息散落：评价在小红书、微信群、WhatsApp 群之间反复转，原始信息丢失严重
  • 主观且不可比："水课"对 A 是水课，对 B 可能 workload 极大，缺乏结构化标签
  • 隐私顾虑：敢在公开平台给差评的人很少；想做详细评价但又怕被认出来
2

核心痛点

在动手做之前，我先调研了 12 位 ECIC 在读学生和 4 位往届毕业生，发现：

  • 73% 的人在选课前至少问过 3 个学长姐，但得到的回答常常互相矛盾（"我那年 A 教授很 nice，今年换了 B 教授就..."）
  • 没有任何一个集中的、结构化的、可对比的评价来源
  • 愿意公开给差评的人极少——大家怕被认出来
  • 选课小助手类的需求：大家想要"按我的偏好自动排"的功能（"我不想要考勤、不要期末考、workload 轻"）
判断：这不是"做个展示页面"能解决的——需要做"工具"，不是"内容站"。
约束：纯静态站、隐私优先、不能依赖后端。
3

解决方案 & 效果

网站设计了4 个核心功能，每个功能都直接对应一个具体痛点：

功能 1：课程评价浏览 + 标签筛选

26 门课 × 真实学长姐评价 × 10+ 标签（考勤、workload、数学要求、给分等）。支持按 ICOM / ECOM / FITE / COMP 分类筛选。

课程评价页 · 标签化展示 + 分类筛选

功能 2：选课小助手（按偏好自动排序）

用户勾选"无考勤 / 无期末考 / 工作量轻"等标签，工具自动筛出满足条件的课程；用户给每门课打 1-5 星，右侧自动排出个人优先级。

选课小助手 · 标签筛选 + 个人打分排序

功能 3：课程对比（最多 3 门并列）

把候选课程并排看评分、学分、标签、简介——避免"忘了这门的细节"的尴尬。

课程对比 · 一屏看清 3 门候选课

功能 4：我的收藏（只存本机）

收藏的课只存在用户自己浏览器里，换设备或清缓存就消失——换句话说，永远不会被别人看到。

技术栈

技术栈选型的核心思路是 "用成熟方案降低维护成本 + 用隐私优先设计降低用户顾虑"：

React 19 TypeScript Vite Tailwind CSS v4 React Router localStorage GitHub Actions CI/CD

选型理由：用 TypeScript + React 保证类型安全和组件复用；用 Vite 拿到秒级 HMR；用 Tailwind CSS v4 保持视觉一致性；用 localStorage 实现"用户数据只存本地"的隐私设计——数据天然不上传、零运维成本。

持续部署：GitHub Actions 自动构建 + GitHub Pages 静态托管，改课程数据 push 即上线，不需要任何人手工操作。

核心代码片段

展示 3 段最体现产品设计的代码：

① 评分算法：学长姐评价取平均

简单但严格——没人给分就返回 null，不显示假评分。

/** 学长姐评价的平均分，没有人给分则返回 null */
export function avgRating(course: Course): number | null {
  const scores = course.reviews
    .map((r) => r.rating)
    .filter((r): r is number => typeof r === 'number' && r > 0)
  if (scores.length === 0) return null
  return scores.reduce((a, b) => a + b, 0) / scores.length
}

② 标签筛选：必须全部命中

用户勾选多个标签 = 多个条件都满足。这是我在用户访谈里听到最多的需求（"我既要无考勤也要无期末考"）。

/** 课程是否包含全部所选标签 */
export function hasAllTags(course: Course, selected: string[]): boolean {
  return selected.every((t) => course.tags.includes(t))
}

③ 隐私优先：所有用户数据只存 localStorage

从 storage.ts 的注释可以直接看出设计意图——访客数据严格隔离在用户自己的浏览器里。

/**
 * 本站没有后端，所有东西都在浏览器 localStorage 里：
 *
 * 1. COURSES_KEY —— 管理员在本机编辑的课程数据
 *    只影响这台电脑这个浏览器，不会同步给任何访客。
 *
 * 2. RATINGS_KEY —— 访客自己的打分
 *    每个人只存在自己浏览器里，彼此看不见、不上传、不统计。
 *    清缓存即消失。
 */
6

AI 搭建思路

这个项目从 0 到 1 上线，我主导了产品决策和验收，AI 负责实现细节。流程大致是这样的：

第一轮：把"想要什么"翻译成"约束清单"

我先把场景、痛点、约束、边界、验收标准列清楚（"用户打分只存本地""部署零成本""课程数据写在 src/data/courses.ts"），再让 AI 给方案。问题模糊时，AI 给的方案也会模糊——前 30% 的工作量其实在"想清楚要什么"。

给 Claude 的第一段 prompt 差不多是这样的：

我要做一个港大 ECIC 学院的选课参考网站。

硬约束：
1. 不依赖外部数据库
2. 用户打分只存自己浏览器 localStorage，绝不上传
3. 部署到 GitHub Pages 之后零成本运行
4. 课程评价数据写在 src/data/courses.ts 里，由我手动维护

功能：课程列表 + 标签筛选 + 选课小助手 + 课程对比 + 收藏夹

技术栈偏好：React + TypeScript + Vite + Tailwind CSS

先给我项目结构，再给我首页设计建议。

第二轮：用"反例"逼 AI 暴露边界

拿到第一版方案后，我不直接开干，而是问：

  • 如果用户清缓存，我之前打的分没了，这个体验能不能接受？
  • 如果 100 个学生同时打分，会不会把 storage 写满？
  • 如果用户开了多个标签，结果一门课都筛不出来，怎么提示？

每问一次，AI 都会补充一些我没想到的边界条件。这些"反例"是 AI 方案最容易漏的部分——必须主动问。

第三轮：分模块迭代，每步验收

整个项目拆成了 6 个模块（评价页、小助手、对比、收藏、详情页、管理后台），每完成一个就让 ECIC 的朋友试用、提反馈、再迭代。

最关键的一个决策："个人打分不上传"——这是 AI 第一版默认想做的（"方便做数据统计"），我坚持砍掉。砍掉的判断标准很简单：用户没明说要、做了反而增加隐私顾虑、删了不影响核心功能。

7

踩坑与心得

踩坑 1：标签系统一开始设计得太复杂

我让 Claude 给每门课加 30+ 个细粒度标签（"3 次作业"、"1 次小组展示"），结果筛选面板堆成一坨，用户根本看不懂。
修正：砍到 4 大类 22 个标签，颜色按"好事/坏事/中性"区分。UI 瞬间清爽。

踩坑 2：以为"管理员后台"是必要的

第一版我做了个管理员后台（用口令进入），可以在线编辑课程数据。技术上看很完整，但实际用起来：我每次都忘了口令，最后还是直接改 courses.ts 提交代码。
修正：把管理员后台砍掉，保留口令逻辑但只用作"防手滑"装饰。

踩坑 3：以为"评分"会让评价更有用

1-5 星评分是产品默认设计，但实际访谈里发现：用户更想看"具体标签"（无考勤、workload 大），而不是"综合分数"。
修正：评分降为辅助指标，主要用标签做筛选。1-5 星只在对比和收藏页辅助显示。

这个项目教会我的事：AI 搭得很快，但"砍需求"比"加需求"难。好的产品不是功能多，是砍得准。
