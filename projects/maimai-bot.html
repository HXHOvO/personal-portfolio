脉脉自动化工作台

给 HR 同事"双击就能用"的脉脉工具。覆盖 4 个动作（搜索 / 投递审核 / 访客触达 / IM 分诊），支持 AI 智能判断。
这个项目最有价值的不是工具本身，而是撞反爬时用 A/B 实验定位触发点的方法论。

Node.js + CDP DeepSeek 方法论案例 非技术用户 A/B 实验
1

项目背景

团队 HR 同事在脉脉上要做 4 件事，全是重复劳动：

  • 搜索人才：按条件翻人才库、加好友、发消息
  • 投递审核：每天几十份投递，逐条判合适/不合适
  • 访客触达：对看过职位的访客发起"立即沟通"
  • IM 红点分诊：候选人的未读消息分类 + 给回复建议

HR 同事说："这些事又慢又烦，但我们不会写代码，也不该碰命令行。" 需求评审时，我们定了两条硬指标：

硬指标 1：能替人干——搜索、筛选、触达、投递审核、消息分诊这些动作链都要能批量跑。
硬指标 2：给非技术同事用——双击启动、点选界面、实时看进度，黑框报错和命令行一律不暴露。

评审时还砍掉了一个伪需求——"批量打招呼"。脉脉平台自己就有，做了没有增量价值，直接不做。 结论先行：只做平台没有、且能省下重复人力的动作。

2

核心痛点：撞上反爬

工具开发过程比预想中难。最初想走现成的浏览器自动化框架（Playwright 这类），结果：

  • 脉脉侧：哪怕只是读页面（不点不发，纯翻页取文本），登录态也会被网站直接踢掉，连试 5 次全挂。
  • Boss 侧：流程跑着跑着页面就自己刷新（reload），动作链被打断。

怎么发现这是反爬的？不是看报错，是看现象规律—— 失败不随机，总在"自动化一介入"就发生，手动操作却从不触发。 这说明网站前端有一套检测自动化的逻辑，能认出"这不是真人在操作"。这就是反爬。

关键判断：反爬最难的不是绕过，而是先搞清楚到底哪一步动作触发了它。 一整套流程里有几十个操作，逐个猜会猜疯。
3

解决方案：用 A/B 实验定位触发点

方法：把反爬当"控制变量实验"来做

不靠猜，靠实验：

  1. 建对照组：克隆一个能跑通的参照实现作为 A 组，自己的实现作 B 组，同账号同页面对比
  2. 最小化变量：写一批只做单一动作的探测脚本（只连接、只读一次、只点一次……），一次只开一个"嫌疑"能力
  3. 逐步加回：从"什么都不做"开始，一项项把能力加回去，盯着哪一项一加回去就触发刷新/踢登录
  4. 反复验证：定位到嫌疑点后，单独开/关它跑多轮，确认是它、不是巧合

真实教训：一次误判

Boss 项目一开始我误判成"读取页面这个动作"本身有问题。 靠 A/B 多轮才纠正过来——真正的触发点是某个"开启高级调试能力的开关"，而不是读取动作本身。

没有 A/B，这种误判会带着整个项目走错方向。
这一节是整个分享的核心方法论：面对黑盒反爬，不靠猜，靠控制变量实验。

破局思路：把反爬约束前置到需求里

定位清楚后，规避方法反而简单。关键转变是：反爬约束在提需求时就讲死，让工具从第一行就长在安全的地基上，而不是出了问题再打补丁。

给 AI Agent 的"技术约束清单"是这样的：

我需要你帮我写一个脉脉网站的自动化工具。请严格遵守以下技术约束：

核心原则：绝对不能往网页里注入任何 JavaScript 代码。

1. 用 --remote-debugging-port=9222 启动 Chrome，通过 CDP 连接
2. 用 Node.js + 调试协议来操作
3. 只允许使用 DOM 域（读页面结构）和 Input 域（模拟鼠标/键盘）
4. 严禁使用任何"执行 JavaScript"的方法
5. 点击流程：先取元素坐标，再模拟真实鼠标点击
6. 每次操作之间加 2~4 秒随机延迟，模拟人工节奏

把约束前置 = 把"踩过的坑"变成"不许踩的规则"。 新接手的人照着做就不会重新触发反爬。

4

技术栈

Node.js chrome-remote-interface DeepSeek Express (Web UI) CDP DOM/Input 域 独立 Chrome profile

关键设计：用一个独立的 Chrome profile（--user-data-dir）跑工具，和 HR 同事日常用的 Chrome 完全隔离。 这避免两个原因：① HR 平时手动操作被工具"污染" ② 工具的登录态不会影响日常浏览器。

5

核心代码片段

① 启动脚本：找 Chrome、装依赖、起独立窗口

这个 .cmd 是给非技术 HR 用的——双击就行，零命令行知识。它会自动找 Chrome、装依赖、起专用浏览器、开工作台 UI。

@echo off
title Maimai Workbench
cd /d "%~dp0"

:: 1. 找 Chrome（不写死路径，挨个常见位置试）
set "CHROME="
if exist "%LOCALAPPDATA%\Google\Chrome\Application\chrome.exe" set "CHROME=%LOCALAPPDATA%\Google\Chrome\Application\chrome.exe"
if not defined CHROME if exist "%ProgramFiles%\Google\Chrome\Application\chrome.exe" set "CHROME=%ProgramFiles%\Google\Chrome\Application\chrome.exe"
if not defined CHROME if exist "%ProgramFiles(x86)%\Google\Chrome\Application\chrome.exe" set "CHROME=%ProgramFiles(x86)%\Google\Chrome\Application\chrome.exe"

:: 2. 装依赖（首次运行）
if not exist "node_modules" (
    echo First run: installing dependencies...
    call npm install
)

:: 3. 起独立 Chrome（端口 9223，独立 profile，**和日常 Chrome 隔离**）
start "" "%CHROME%" --remote-debugging-port=9223 --user-data-dir="%~dp0.isolated-browser\maimai-chrome" --no-first-run "https://maimai.cn/ent/v41/recruit/talents"

:: 4. 启工作台 UI
node server\server.cjs --open

② AI 配置：HR 只需填一个 key

所有 AI 能力（搜索质检、IM 分诊）都接 DeepSeek。HR 只需要把 key 填到这个 JSON，其他不用管。

{
  "baseUrl": "https://api.deepseek.com",
  "apiKey": "sk-xxxxxxxx",
  "model": "deepseek-v4-pro"
}
产品设计："填一个 key" 这种事 HR 还能接受，让她写 prompt 她就会放弃。 所以 AI 智能判断的 prompt 都内置在工具里，HR 只勾"用 AI 质检"，不让她写 prompt。
6

AI 搭建思路

第一步：先观察，再设计

撞上反爬之前，我先后问了 Claude 三次"这个方案会不会触发反爬"，Claude 都自信地说"不会"。 第一次我信了，结果翻车了。第二次我半信，自己写了对照实验，结果发现 Claude 的方案里藏了一个被忽略的反爬触发点。

从那以后我就养成了习惯：AI 说的"不会出问题"都先当"可能会出问题"对待，自己写实验验证。

第二步：把"踩过的坑"做成"约束模板"

第一次撞反爬时 Claude 给我的是"出问题再 patch" 的思路，每次 patch 一次。 反复几次后我意识到：应该把"所有已知的反爬红线"列在 prompt 最前面，让 Claude 第一版就避开。

这其实是个通用的产品方法论——把"事故经验"前置到"产品需求"里。

第三步：让 HR 验收，不是我验收

第一版做完后我自己测了一遍觉得 OK，结果给 HR 试的第一天就被骂："这个按钮在哪？""为什么弹这个框？""错误提示我看不懂"。
教训：产品的"用户"不是技术 HR，也不是我自己，是连命令行都没碰过的非技术 HR。

于是我重做了 UI：所有动作点选就行，所有错误用人话，所有进度可见。

7

踩坑与心得

踩坑 1：把"自动化"等同于"功能强大"

第一版我做了 8 个动作。HR 同事看完说："我常用的是这 4 个，剩下的我记不住也不想用。" 于是砍到 4 个。
学习："功能多"不等于"产品好"。减法比加法难。

踩坑 2：让 HR 写 AI prompt

第一版让 HR 在界面里填"AI 质检口径"（如"只要字节后端、阿里中台可标存疑、其他不符"）。 HR 说："我连打字都不想，你给我预设几个常用模板我勾就行。"
修正：预置 5 个常用 AI 口径模板，HR 选模板 → 可选微调 → 不用从零写。

踩坑 3：默认"自动拒绝不合适的候选人"

第一版自动对"不合适"的人发拒绝消息，HR 同事用了 3 天就喊停： "我怕 AI 判错，万一真合适的人被拒了怎么办？"
修正：默认"自动通过合适的"，不合适的留人工。"AI 不该替 HR 做不可逆决定"。

这个项目教会我的事：好的产品不是 AI 多聪明，而是AI 知道什么时候该停下来等人类。 这也是做 AI 产品最难的部分：设计"AI 不能做"的边界，比设计"AI 能做"的功能更重要。
